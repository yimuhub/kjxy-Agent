# v3.21–v3.23 方案：体验修复、信息架构重构、一句话业务与设备数据智能

> 日期：2026-10-29　状态：A（3.21.0）已交付，B（3.22.0）/ C（3.23.0）待开工　版本纪律：只递增 3.x 小版本（3.21.0 / 3.22.0 / 3.23.0）
>
> 依据：本轮你提出的 7 条反馈 + 对当前代码与运行中服务的实测核查。文中所有「现状」均标注了文件与行号，便于逐条对照。

## 0. 结论摘要

| 批次 | 版本 | 主题 | 你最终会看到什么 |
|---|---|---|---|
| A | 3.21.0 | 体验修复与自生长重构 | 批量删除可用；能力卡片直达「我的智能体」（跟随你自定义的菜单名）；群聊加人弹窗可搜索；自生长管理一个页面管完 Skill（中文状态、点名称看说明、自动升级开关）；专家审核只留知识审核 |
| B | 3.22.0 | 一句话业务 | 台账/诊断/告警工单顶部有「一句话」输入：说一句 → 预览 → 确认，就完成新增；复杂表单仍保留 |
| C | 3.23.0 | 设备数据智能分析 | 设备读数自动做趋势/异常/阈值/组合风险分析，生成带数字依据的洞察与建议，可一键转工单，支持定时分析 |

推荐顺序：**A → B → C**。A 是修复与止血，改动集中、风险最低；B 复用 A 之后的界面骨架；C 依赖数据底座与调度，放在最后做深。

## 1. 逐条现状与处理方案

### 1.1 「批量删除」报「当前后端版本不支持该操作」——是后端进程旧了，不是功能没写

**实测证据（只读探测你正在跑的 8000 端口）**：

```
POST http://127.0.0.1:8000/api/v1/chat/sessions/batch   → 405
GET  http://127.0.0.1:8000/api/v1/ping                  → 200
```

**根因**：批量接口本身存在（`backend/app/modules/chat/router.py:224`，v3.15 已上线），但 8000 端口上的进程启动早于该接口。FastAPI 把 `POST /chat/sessions/batch` 匹配到只允许 DELETE 的 `/{session_id}`，于是返回 405；前端把 405 统一映射成「当前后端版本不支持该操作，请重启后端服务后再试」（`frontend/src/utils/status.ts:68`、`:74`）。

**处理**：

1. **立即口径（不改代码）**：在 `backend/` 下执行 `alembic upgrade head`，然后重启 8000 端口的后端进程。重启后「批量删除」应立即可用。（我不会去杀你自己的进程；若你允许，我可以给一条明确的命令清单。）
2. **不再让用户猜版本**：新增 `GET /api/v1/meta`，返回 `{version, migration_head, features: [...]}`；前端启动时比对，发现后端版本落后就显示可关闭的横幅：「后端 vX 缺少「批量会话」能力，请升级并重启」，而不是把错误留到用户点按钮时才出现。
3. **文案更可行动**：405 文案改为「后端版本较旧或该接口未启用：请先执行数据库迁移并重启后端；若已重启仍出现，请反馈此页面」。
4. **验收**：重启后批量删除真实可用；人为把后端换成旧代码时，横幅能识别；E2E 增加一条「批量删除 2 条会话」的用例。

### 1.2 能力卡片「在能力中心查看」→ 直达「我的智能体」，并跟随自定义菜单名

**现状证据**：

- 后端卡片动作文案写死「在能力中心查看」（`backend/app/modules/chat/capability.py:161`）。
- 前端点击 `view` 跳的是 `/agents`（专业助手），不是 `/agents/custom`（`frontend/src/components/chat/ChatCard.vue:219-222`）。
- 「我的智能体」菜单名来自可 DIY 的菜单配置，默认值在 `frontend/src/stores/menu.ts:46`，用户可在「菜单 DIY」里改标题。

**方案**：

- 后端把动作文案改成中性「查看智能体」，把「叫什么、去哪儿」交给前端单点决定，避免两处文案漂移。
- 前端用菜单 store 取 `path === '/agents/custom'` 的当前标题（没放进菜单就回退「我的智能体」），渲染为「在{{名称}}查看」，并跳转 `/agents/custom`。
- 同时把草稿卡片的状态文案从「已创建草稿」保留不变（`ChatCard.vue:207`），只改动作的落点与名称。
- **验收**：普通账号看到「在我的智能体查看」；把菜单项改名为「我的 AI 助手」后，卡片文案同步变化且仍落到同一列表页。

### 1.3 群聊「添加成员」弹窗重做：顶部搜索 + 更清晰的视觉层级

**现状证据**：`frontend/src/components/chat/ChatMemberBar.vue:12-80` 目前是 300px 的 `el-popover`，平铺列表，无搜索、无分组、无「已加入」态。

**方案**（改为居中 `el-dialog`，宽 520px）：

1. **顶部搜索框**：打开即聚焦，输入即时过滤（名称 + 简介 + 编码），支持回车选中第一项、Esc 关闭。
2. **分组**：「助手」「班组」两段，段内按最近使用/名称排序；已加入的置灰并标「已在群聊」。
3. **每行信息**：头像/emoji、名称、一句简介、类型标签；右侧「添加」按钮，点一下加入并保留弹窗（支持连续加多人），底部显示「已添加 N 位」。
4. **状态**：加载骨架、空结果（「没有匹配的助手，试试别的关键词」）、加载失败可重试。
5. **可访问性**：`role="dialog"`、搜索框 `aria-label`、列表 `role="listbox"`、键盘上下选择。
6. **验收**：输入关键词 1 秒内过滤；连续添加 3 位不关闭弹窗；已达上限（8 位）时按钮禁用并提示。

### 1.4 自生长管理：合并 Skill 功能、全中文、可点开说明、自动升级开关

**现状证据**：

- 自生长管理（菜单「自我升级」）的 Skill 列表直接渲染英文状态（`frontend/src/views/EvolutionView.vue:62-72`），列只有编码/版本/状态/灰度/操作。
- 专家审核页里的「Skill 管理」与自生长管理的 Skill 列表功能重叠：新建、上传 SKILL.md、导入插件 zip、GitHub 导入、审核发布都在那边（`frontend/src/views/ReviewView.vue:93-286`）。
- Skill 状态枚举来自后端：`draft|testing|pending_review|published|deprecated`（`backend/app/modules/evolution/models.py:69`）。
- 已有自我总结引擎会从证据里生成技能草稿（`backend/app/modules/self_improve/service.py:248`、`:348`），可作为「自动升级」的执行底座。

**方案**：

#### (a) 信息架构合并

- 专家审核页只保留「待审核知识」；删除「Skill 管理」页签。
- 自生长管理改为三个页签：**Skill 列表**（含新建/上传/导入/GitHub 导入/审核/发布/灰度/门禁记录）、**插件**、**运行记录**（自我总结 run 与失败原因）。
- 菜单文案建议：「专家审核」→「知识审核」；「自我升级」保留，页内标题「自生长管理」不变。

#### (b) Skill 列表重做

| 列 | 内容 |
|---|---|
| 名称 / 编码 | 中文名在上、字号大；编码在下、字号小、等宽字体（如 `水稻施肥建议` / `rice.fertilizer.v2`） |
| 版本 | 当前生效版本 |
| 状态 | 全中文：草稿 / 测试中 / 待审核 / 已发布 / 已下线 / 已驳回；AI 生成仍显示徽标 |
| 自动升级 | 开关（见 c） |
| 调用 | 近 30 天调用次数、成功率 |
| 操作 | 详情、审核、灰度、门禁记录 |

- 点**名称**（或整行）打开右侧详情抽屉：名称、编码、一句话描述、适用场景、输入/输出、执行步骤、依赖工具、示例、版本历史、最近评测与签名状态。这就是「这个 skill 能干啥」的固定入口。

#### (c) 自动升级（类似 Hermes 的持续自我提升，但默认不自动发布）

1. **采集**：新增 `skill_usage_events`（yard_id、skill_code、session_id、来源、结果、token、反馈）。在「技能被选中并参与回答」与「技能工具执行失败」两处埋点（实现时确认精确挂载点，候选：`backend/app/modules/agents/declarative.py:1038` 附近的技能注入与 `backend/app/modules/market/skill_agent.py` 的调用路径）。
2. **开关**：新增 `skill_auto_upgrade`（yard_id + skill_code 唯一）：启用、最小调用次数（默认 10 次/7 天）、冷却时间（默认 7 天）、每日 token 预算。
3. **触发**：复用 `yard_jobs` 调度底座（`backend/app/modules/self_improve/models.py`），新增 kind `skill_auto_upgrade`；满足「调用量达标 + 有失败/纠错样本 + 冷却已过」才执行。
4. **执行**：以「当前定义 + 近 N 条主题级证据 + 失败/低分样本」为输入，产出一份**新版本草稿**与升级说明（改了什么、依据是什么）；走 v3.17 的静态检查、评测与签名门禁（`backend/app/modules/evolution/prepublish.py`）。
5. **红线**：自动升级**只产草稿**，绝不自动发布；没有足够证据、LLM 不可用、超预算时如实跳过并记录原因；不把会话原文写进技能或日志。
6. **界面**：开关旁有「升级记录」入口，显示每次运行的证据摘要、草稿版本、审核结果；草稿停留在「待审核」，由人决定是否发布。

**验收**：状态全中文；点名称能看到完整说明；开关持久化；构造 10 次调用 + 一次失败反馈后，自动生成一个新草稿并出现在待审核；未达标时不产生空草稿。

### 1.5 农业台账 / 作物诊断 / 告警与工单：一句话就能办

**现状证据**：三页各自有完整的表单弹窗（`FarmView.vue:23`「新增地块」、`DiagnosisView.vue:240`「新建作物诊断」、`WorkOrderView.vue:297`「新建工单」），字段多、路径长。

**方案：统一「一句话」条 + 预览确认，不牺牲可追溯性**

1. **交互**：每页顶部一个输入条（占位文案随场景变化），例：
   - 台账：「新增地块 东一号田 水稻 12 亩，沙壤土」
   - 台账：「东一号田 今天追肥 尿素 5 公斤，王师傅」
   - 诊断：「东一号田 水稻 叶片发黄有褐斑，最近连阴雨」
   - 工单：「把东一号田的虫情告警转成工单，派给张三，明天到期」
2. **两段式**：`POST /quick-actions/preview` 只解析、不落库，返回结构化预览（地块名/作物/面积/日期/责任人/优先级/缺失字段）；用户确认后 `POST /quick-actions/confirm` 落库。**预览阶段零副作用**。
3. **解析策略**：规则优先（名称、数字+单位、日期、人名），不足再交给当前 LLM 产出严格 Schema；两者都失败时明确提示「还缺：面积 / 日期」，并预填到原有表单，不假装成功。
4. **安全**：确认动作走既有服务层与权限校验（不绕过 `farm:write` 等）；全部写审计；一次只做一个动作，不支持「顺便把别的也改了」。
5. **高级入口保留**：一句话条右侧有「用表单填写」，老用户不受影响。
6. **验收**：上述四句各跑通预览→确认→列表可见；缺字段时给可读提示；解析失败不产生任何数据。

### 1.6 设备管理：把「能读数」变成「会分析、给结论」

**现状证据（底座已具备，缺的是分析层）**：

- 设备与读数：`backend/app/modules/devices/models.py:44-90`（webhook 推送 / 连接器拉取，读数 append-only）。
- 指标字典已统一：气温、湿度、雨量、风速、光照、CO₂、四层土壤水分、土温、EC、pH、水位、虫情计数、电量（`backend/app/modules/devices/metrics.py:30-53`）。
- 已有阈值告警规则与设备告警（`devices/router.py:220-300`），告警可转工单（`devices/router.py:145`）。
- 前端只有「数据」弹窗与简单图表（`frontend/src/views/DevicesView.vue:131-160`、`:459`）。
- 已有 `sensor.query` 工具可被智能体调用，但没有「定期自动分析并留结论」的闭环。

**方案分三层：数据底座 → 分析引擎 → 行动闭环**

#### (a) 数据底座补强

- **聚合**：按小时/日生成均值、极值、累计（雨量）、变化率；只算不存原文，必要时落聚合表或按需计算。
- **数据质量**：缺测时段、跳变、越界、长时间不变（传感器卡死）、电量低；质量分随分析结果一起展示。
- **设备健康**：连接器连续失败、最后上报时间、上报频率是否异常（已有部分字段，补可视化）。
- **多设备/多地块对比**：同一指标跨设备对比，标出偏离最大的那台。

#### (b) 分析引擎（规则先行，LLM 只做解释与建议）

新增迁移 `device_analyses`：一次分析 = 一个窗口 + 一组发现（findings）+ 一段结论文本 + 模型与成本。

1. **规则层（确定性、可复核）**：
   - 阈值：沿用设备告警规则的上下限。
   - 趋势：连续 N 小时上升/下降、突变点。
   - 异常：基于窗口均值/标准差的偏离（z-score），并给出具体数值与时间。
   - 农艺组合：如「高湿 + 低温 + 低光照」提示病害风险；「土壤水分骤降 + 无降雨」提示灌溉需求；「虫情计数连续上升」提示防治窗口。
2. **解释层（LLM，可关）**：把规则发现、指标数值、设备位置、作物与近期农事记录组织成有界上下文，生成「发生了什么 / 可能原因 / 建议动作 / 需要人工确认的点」，**必须引用具体数字与时间**，不得编造未采集的指标。
3. **分级**：info / watch / warning / critical；critical 自动生成设备告警并进入既有「告警 → 工单」链路。

#### (c) 运行与呈现

- **触发**：每日定时（复用 `yard_jobs`，新增 kind `device_analysis`）+ 设备详情「立即分析」+ 读数异常时事件触发（后续批次）。
- **界面**：
  - 设备卡片显示「最近分析：warning · 2 条发现」。
  - 设备详情新增「AI 分析」页签：趋势图 + 发现列表（数值、时间、规则、建议）+ 数据质量提示 + 「转工单」。
  - 概览页新增「设备洞察」卡片，只显示需要人处理的发现。
- **成本与诚实边界**：窗口与指标数有上限；无数据/数据太稀薄时明确说「证据不足」，不产出结论；不做设备控制，不做因果断言，用药建议仍走专家复核口径。

**验收**：用种子读数构造「土壤水分连续下降 + 无降雨」，分析产出带具体数值的 finding 并可转工单；同一天重复运行幂等；数据缺失时输出「证据不足」而非空话；定时任务可在运行记录里看到。

## 3. 非目标（本三轮不做）

- 不做设备远程控制、不做自动执行灌溉/施药。
- 不把 Skill 自动升级做成「无人值守自动上线」；发布仍需人工或既有门禁。
- 不做全站自然语言命令中心；一句话入口只覆盖上述四类高频动作。
- 不做跨小院设备数据共享（A2A 已有只读技能边界，另议）。
- 不引入新的前端图表库（沿用现有实现，必要时用轻量 SVG/ECharts 现有依赖核对后再定）。

## 4. 风险与对策

| 风险 | 对策 |
|---|---|
| 旧后端进程导致 405 反复出现 | 版本握手 + 启动横幅 + 运维文档写清「迁移→重启」顺序 |
| 合并 Skill 功能导致权限口径变化 | 复用现有接口与权限点（`skills:manage` / `skills:review`），只搬 UI 不放松后端 |
| 自动升级产出低质草稿、消耗 token | 调用量/失败样本门槛、冷却、日预算；只产草稿；证据不足直接跳过并记录 |
| 一句话解析误建数据 | 预览必须人工确认；确认走服务层校验；一次一动作；审计留痕 |
| 设备数据稀疏导致「AI 胡说」 | 规则层先判定证据是否充分；不足时返回「证据不足」；文本必须带数字与时间 |
| 合并页面破坏既有 E2E | 每批跑全量 E2E，替换选择器而不是删除用例 |

## 5. 交付与门禁（每批一致）
