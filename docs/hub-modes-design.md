# 通用基座 × 运营模式：枢纽层级设计（v3.65，2026-11-04）

> 目标：把平台打造成**通用基座**，其上支持按真实治理形态选择「运营模式」。
> 全国调研（research-china-science-yards-2026-11.md §6.3）给出的三种现实形态
> 各有组织结构差异——本设计把差异**参数化**，而不是分叉出三个产品。

## 一、四种运营模式（对应调研实证）

| 模式 key | 名称 | 现实原型 | 组织结构 | 枢纽侧重 |
| --- | --- | --- | --- | --- |
| `province` | **省级科协模式** | 江苏（省科协评审、89 家分布 13 市） | 多个「培养单位/省级联络站」枢纽，小院分散跨市 | 跨市分散、按高校聚合、达标监测 |
| `municipal` | **市级全域模式** | 邯郸（一市 42 院、20 县全覆盖） | 单个「市级专班」强枢纽，县域节点 | 县域覆盖地图、全域推广进度 |
| `station` | **实验站枢纽模式** | 曲周（实验站统管十多个小院、一院一策） | 实体实验站深度管理小院群 | 小院群横向对比、类型多样（一院一策） |
| `standalone` | **独立小院** | 通用默认（现状） | 无枢纽，单小院自用 | 不出现枢纽界面 |

**关键决策**：mode 挂在**枢纽（hub）**上而不是平台上——同一个平台（通用基座）
可以同时存在不同模式的枢纽（现实中一个供应商完全可能同时服务江苏某高校、
邯郸某专班、曲周某实验站）。平台级不做强制统一。

## 二、数据模型（迁移 0071）

```
yard_hubs        枢纽：id, name, mode(province|municipal|station|standalone),
                 region(省市描述), note, created_by
hub_members      枢纽成员：hub_id, user_id, role(manager|viewer)，(hub_id,user_id) 唯一
yards.hub_id     小院归属枢纽（可空；一个院最多属一个枢纽）
```

- 权限点：`hubs:manage`（创建/编辑枢纽、绑定小院、管理成员——platform_admin
  与 hub manager 默认）；`yards:aggregate` 继续承担「跨院看数字」的边界。
- 聚合口径：枢纽工作台 = 监管看板（/journal/aggregate）的**收窄版**——
  只统计 `yards.hub_id = 本枢纽` 的小院，只出数字与时间，不含日志内容
  （隐私边界与监管看板一致）。

## 三、模式差异的呈现（参数化而非分叉）

聚合查询与数据模型四种模式完全共用；差异只体现在**工作台文案与侧重**：

| 模式 | 工作台标题 | 侧重卡片 |
| --- | --- | --- |
| province | 「培养单位枢纽 · 省级科协模式」 | 各院达标进度（100 篇锚点）排序 |
| municipal | 「市级专班 · 全域推广模式」 | 县域覆盖（按 region 分组计数）与断更 |
| station | 「实验站枢纽 · 小院群模式」 | 小院群横向对比 + 「一院一策」类型分布 |
| standalone | 不出现枢纽界面 | — |

实现：前端按 `hub.mode` 渲染标题与侧重卡（术语表），后端返回同一份聚合数据 +
`mode` 字段。新增模式 = 加一枚举 + 文案，不动结构。

## 四、角色与登录

- hub manager 登录后默认落地「枢纽工作台」（/hubs）；
- platform_admin 可创建枢纽、指派 manager；manager 可绑定/解绑小院、看聚合；
- 小院负责人不受影响（枢纽只读聚合，不干预小院内部管理）。

## 五、分期

- **P0（本轮）**：模型/迁移/服务/端点 + 枢纽工作台（模式选择、绑定小院、
  聚合收窄、断更预警）+ 落地页 + 测试。
- P1：枢纽周报自动推送（weekly 聚合按枢纽出一份）、县域节点层（municipal 的
  县粒度）、跨枢纽横向对比（platform_admin）。
- P2：术语文案包抽离、多语言（国际化预留）。
