## 2. 维度一 · 资深开发工程师视角

### 2.1 阻断级（🔴 P0）

1. **首启向导完全不落库，且把用户困在死循环。**
   - `frontend/src/views/SetupWizard.vue:406-420` 的 `next()` 只做校验与 `cur.value++`；`goLogin()`（:426-428）只 `router.push('/login')`。文件里注释声称"完成后调 `/setup/initialize`"（:320），但 `setupApi.initialize`（`frontend/src/api/setup.ts:36-45`，且返回 `access_token`）**全仓无任何调用**。
   - `frontend/src/router/index.ts:260-266` 守卫：任意非 `/setup` 路径在 `initialized=false` 时强制跳回 `/setup`；而 `stores/auth.ts` 的 `ensureSetupStatus()` 缓存该结果。于是"进入系统→/login→守卫→/setup"形成**不可退出循环**。
   - 后果：院内服务器版/云端版**首次部署无法通过 UI 建出第一个管理员**，只能直接打后端 `POST /setup/initialize` 或走桌面 bootstrap。
   - 修复：在 `next()` 到达第 6 步时组装 `SetupInitializePayload` 调 `setupApi.initialize()`，成功后持久化 token 并 `router.replace('/')`；把 `submitting` 真正用于 loading（当前 `:296` 绑定了 `submitting` 却从不置真）。

2. **模型/供应商出口未统一 `trust_env=False`，特定环境直接硬崩。**
   - 复现：`NO_PROXY` 含 `[::1]`（很多开发机/企业机默认如此）时，`httpx.AsyncClient()` 解析代理链抛 `InvalidURL: Invalid port ':1]'`。
   - `backend/app/modules/llm/supplier_service.py:652`（探测）、`:795/:1737`（其他出口）、`providers_openai.py:118`（**主对话出口**）、`images.py:195`、`video.py:244/379`、`chat/multimodal.py:93` 均为默认 `trust_env=True`。
   - 反观较新模块已正确规避：`search/providers.py:42`、`search/egress.py:236`、`cluster/service.py:202`、`tools/custom_runtime.py:102` 都显式 `trust_env=False`。**同一仓库内标准不统一**。
   - 后果：探测接口 500；主对话在同样环境下会整条链路硬崩（不止探测）。
   - 修复：所有面向上游模型的出口统一 `trust_env=False`，并给 `NO_PROXY` 做 IPv6 括号容错；补一条"`NO_PROXY` 含 `[::1]` 时探测仍 200"的回归用例。

### 2.2 高（🟠 P1）

3. **模型状态展示与实际调用不一致，误导运维。**
   - `backend/app/modules/llm/service.py:30` 在 `llm_provider=="fake"` 时直接判定 Mock；而真实调用走 binding 解析链（实测日志"选择了模型提供方 supplier:agnes-main"）。结果"设为当前"后，页面顶部仍写"演示/Mock、没有可用供应商"，与真实计费行为矛盾。

4. **异步路径里混入同步阻塞与会话锁。**
   - 129 个 `async def` 注入同步 `Session`；`chat/stream.py:_runner` 在事件循环内做同步 commit；`commander/service.py:154/186/195` 在异步调用链里用进程内锁 + `time.sleep`。高并发/多 worker 下易拖垮事件循环。

5. **首启可并发建双超管。**
   - `setup/service.py:84` 仅"读判 `is_initialized`"，无唯一闸/无锁；`setup/router.py:48` 匿名且无限流。并发两个初始化请求可能各建一套超管/小院。

### 2.3 中（🟠/🟡 P2）

6. **巨石与横切重复**：`commander/service.py`(2752)、`chat/service.py`(2162)、`llm/supplier_service.py`(2043)、`library/service.py`(2024)、`agents/declarative.py`(1837)；邮箱脱敏 `insights/service.py:105` 与 `yards/member_service.py:61` 两套口径；`mask_url` 在 `mcp/service.py:36` 与 `push/service.py:84` 逐字重复；时间处理 34 处各写一份（`core/timezone.py` 已存在）；权限守卫四份（`core/deps.py:102`、`yards/router.py:38`、`quota/router.py:35/47`、`branding/router.py:56`）。
7. **契约/DTO/错误码不规范**：83 处 `response_model=None`，OpenAPI 无出参契约；`core/errors.py:10` 错误码为自由字符串，约 200 个字面量散落无枚举；`contracts/error-codes.md` 仅覆盖 8 处。
8. **可观测性薄弱**：`/metrics` 默认关闭且为进程内计数（多 worker 失真），无分布式追踪。
9. **测试盲区**：仓库内**没有任何 audit 相关测试**（`find tests -name "*audit*"` 为空），所以"先 commit 再写审计日志、路由不 commit 导致审计丢失"（`billing/service.py:325-336` 等）长期无回归。
10. **死代码/空实现**：`llm/official_service.py:68-114` 的 `MockOfficialChannel/get_channel` 全仓无调用；`setup/service.py:185-187` 的 `journal_enabled` 分支体为 `pass`（假开关）。

### 2.4 运行效率

- **单句回答两跳模型**：同步实测 31s（路由分类 + 生成），且流式路径在该次实测中"两次 200 后无产出"。首字延迟对生产力工具是致命的。
- **工具失败即卡死**：指挥官/工具链命中 Brave `429` 后无超时/退避上限，界面锁死（见 §3/§4）。
- **N+1**：`admin/router.py:66-73` 每小院 2 次 count；`library/service.py:818-828` 逐 key 查两表。

## 3. 维度二 · 资深产品经理视角

1. **信息架构过载（🟠）**：左侧一级/二级入口 20+（工作台/小院监管/枢纽/智能对话/指挥官/能力协作/能力中心/自我升级/知识数据/知识库/农业台账/作物诊断/告警工单/任务/设备政策/管理与统计/用量额度/专家审核/小院管理/负责人驾驶舱/模型中心/成员/系统设置/IM）。对"葡萄种植户"这一目标人群，认知负担远超其日常任务所需。
2. **术语漂移（🟠）**：路由标题与菜单文案不一致（如 `router:178/148/172` 与 `menu.ts:59/63/70` 的"助手/智能体/智能对话/通用对话"混用），小白会把"能力中心/智能对话/指挥官"当成三个不同产品。
3. **默认路由过度"指挥官化"（🔴 高）**：输入"介绍你自己"这类零工具需求，被指挥官规划成子任务并触发联网搜索（Brave 429）。产品应"先给最快正确答案，只有明确需要编排时才升级到指挥官"。
4. **状态自相矛盾（🟠）**：已配置真实供应商且 `is_active:true`，页面仍写"演示/Mock、无可用供应商"；这会让运营/客户成功误判"没接上模型"。
5. **付费入口埋点不合理（🟠）**：账单入口 `QuotaView.vue:605` 需要 `insights:read` 权限（`router:184`），普通成员看不到；`chat.ts:519` 触发 `QUOTA_EXCEEDED` 时，弹窗 `ChatPanel.vue:873` 只给"申请提升额度"，**没有"购买/兑换"CTA**，转化断点。
6. **付费流程是占位（🔴）**：`llm/official_service.py:416` `payment_url` 注释即"支付网关未接入前的占位地址"；到账靠兑换码或管理员手工确认。`BillingPanel.vue:11` 也明写"支付网关接入前…示例价"。
7. **扩展性/一致性（🟡）**：`api/modules.ts` 已 3062 行且仍集中；`el-dialog` 散落 60 文件，仅 `AsyncState.vue` 一个共享态组件；字段级校验仅 `MembersView` 用 `:rules`，其余手工校验（`DevicesView.vue:475/486/491`），错误提示不一致。

## 4. 维度三 · 重度用户视角（生产力工具标准）

1. **"顺手程度"不达标（🔴）**：一条一句话的确认，同步 31s；流式路径我实测直接"假死"（停在正在选择助手）。重度用户每天几十次交互，这种首字/失败体验无法形成依赖。
2. **可挽回性差（🔴）**：失败或长时间无响应时，缺"停止生成/重试/切换模型"的就地入口；我实际只能刷新页面，而刷新会把流式记录成"已停止生成（ABORTED）"，且服务端仍在跑，紧接着的新消息会排在后面继续卡（新会话按钮被禁用）。**客户端 abort 并不会取消服务端 run**。
3. **工具链脆弱（🔴）**：联网搜索命中 429 后没有"降级为不搜索直接答"的兜底，整条回答被连带拖死。
4. **价值产出可期但要等（🟢/🟠）**：能力面很宽（文档/PPT/图像/视频/知识库/诊断/工单/台账/班组/自生长），一旦主链路稳定，确实有"一句话到成品"的潜力；但目前"潜力"大于"当下可用"。
5. **信任成本（🟠）**：无 token 级流式输出时，用户看不到"模型在写"的过程，只有静态步骤文案，长等待的焦虑被放大。

## 5. 维度四 · 小白用户视角（首触 → 是否给第二次机会）

1. **首次上手中断（🔴 阻断）**：认真填完 6 步（超管、口令强度、小院信息、品牌色、功能开关），系统郑重显示"配置已写入系统"，点"进入系统"却被弹回向导——**没有任何账号被创建**。这几乎是"第一次就劝退"。
2. **登录后退回（🔴 阻断）**：即便通过后端建号登录成功，任何未初始化判定都会把用户推回 `/setup`，小白无从理解，只会认为"这软件坏了"。
3. **口令规则不一致（🟡）**：注册页提示"6 位"（`SignupView.vue:69`）而向导要求"至少 10 位"（`SetupWizard.vue:419`），首次就踩坑。
4. **会不会给第二次机会（判断）**：**大概率不会。** 首启是产品唯一的"第一印象窗口"；当前首启失败且伪装成功，属于最不可接受的失败形态。若把 §2.1 的两条 P0 修好，配合"三步上手"引导（`FirstRunGuide` 目前只在 `Dashboard.vue:21` 出现），留存仍有救。

## 6. 维度五 · 资深运营经理视角（运营价值 / 引导付费 / 付费意愿 / 升级动力）

1. **价值传导路径清晰但"最后一公里"断（🔴）**：产品能用"一句话出成品/派助手/自动巡检"讲价值，但**支付网关未接入**、权益不扣减，商业化闭环不成立。
2. **付费权益不扣减（🔴）**：`official_entitlements.quota_used` 全仓仅"初始化/读出"，调用链**无 entitlement 校验**——买了"不限量"就真不限量，无法按量计费与阶梯升级。
3. **回调状态机缺闸（🟠）**：`official_service.py:592-598` 不校验订单状态，`:496-500` 把已存在权益改回 `active`；退款后新 `event_id` 可"复活"权益，存在资金/合规风险。
4. **引导付费的触点设计不足（🟠）**：额度耗尽弹窗只有"申请提升额度"，没有"购买套餐/使用兑换码/查看权益"的分流；小院管理员与成员看到的入口不一致。
5. **升级动力（判断）**：当前更像"内部试点/演示版"，缺少"用量可视化→瓶颈提示→一键升级"的增长闭环。建议按"免费额度→超限引导→套餐对比→权益到账→用量看板"做一条最短转化链，并把"官方供应商"作为默认首选通道。
