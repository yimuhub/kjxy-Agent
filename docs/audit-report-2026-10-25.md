1. **最强的资产不是“多智能体”概念，而是“带引用的回答 + 专家纠错可沉淀为知识”这条闭环。** 它同时解决农业场景最要命的两件事：不敢信、没人沉淀经验。

## 2. 整体优势

### 2.1 工程侧

1. **模块边界真实存在，不是“目录分层”。** `api/v1` 只做鉴权/校验/调用，领域逻辑在 `modules/*`，工具、LLM、知识、审批各自闭环；新增作物包/政策包不需要改主流程。
2. **契约意识强。** 统一 `/api/v1`、统一成功/错误包、`request_id` 贯穿、`contracts/openapi.yaml` 与错误码有 CI 漂移检查；这在国内同规模项目中并不常见。
3. **安全基线不空谈。** 租户强制过滤、跨租户 404、密码哈希、供应商密钥 Fernet 加密、配对令牌一次性与类型隔离、SSRF 防护、审计日志、审批 TTL/次数限制均已实现。
4. **可运维性好。** 健康检查拆成 live/ready/worker；Docker、macOS/Windows/Linux 原生、服务器 systemd 三套部署；迁移 19 个版本；发布有 Tauri updater。
5. **测试量真实。** 655 个后端测试覆盖权限、审批、租户隔离、RAG、设备、机器人等，说明团队把“能跑”当成底线而不是口号。

### 2.2 产品侧

1. **主闭环成立且可演示。** 上传文档 → 解析切块 → 检索 → 带引用问答 → 反馈纠错 → 候选知识 → 专家审核 → 入库，全链路真实跑通。
2. **“专家在环”设计有行业价值。** 农业知识高度依赖土专家，平台把“纠错”变成可审核、可追溯、可版本化的知识资产，这是比“接个大模型”更深的壁垒。
3. **能力面覆盖了农业小院的真实工作。** 问答、任务、设备、政策、班组、IM 机器人、桌面端，不是纯聊天 Demo。
4. **多智能体不是摆设。** 总控路由、专业助手、协作班组、Agent 工厂、技能市场、灰度与评测门禁都有实际代码与接口。
5. **视觉体系有辨识度。** 深色玻璃 + 品牌“阗策” + 统一设计令牌，截图观感明显高于常见中后台模板。

### 2.3 UI 侧

- 登录页、工作台、知识库、专业助手、专家审核的视觉一致性良好，卡片、标签、空状态、按钮层级统一。
- 工作台把“上传资料 → 提问 → 反馈纠错”做成三步新手引导，并给出一句话示例问题，这是正确的产品引导方向。
- 风险等级、任务状态、引用来源等关键信息有颜色与文本双编码（部分页面仍只靠颜色）。

## 3. 缺陷清单

> 严重度定义：P0 = 越权/数据破坏/主流程阻断，必须两周内修；P1 = 明显功能错误或高频体验断点；P2 = 工程质量、性能、可维护性与体验优化。

### 3.1 P0（必须先修）

#### P0-1 工具审批存在入参旁路，`approved=true` 可绕过人工审批

- 证据：`backend/app/modules/tools/registry.py:60-70`，`_is_approved` 直接采信 `params.get("approved") is True`；`:194` 仅在 `_is_approved` 为假时才创建审批单。
- 可利用条件：工具 `input_schema` 未禁止额外字段。内置 `workorder.dispatch` 设了 `additionalProperties: false`（`workorder_tool.py:39`），当前不能被利用；但 MCP 桥接工具在 schema 缺失时退化为 `{"type": "object"}`（`backend/app/modules/mcp/tool_bridge.py:250-251`），此时客户端传入 `approved: true` 即可跳过审批直接执行外部工具。
- 影响：违反“外部副作用必须人工确认”的安全红线，且会随 MCP 工具数量增加而扩大。
- 修复：删除 `params.get("approved")` 快路径；审批上下文只能由服务端在“审批单已批准且参数哈希一致”后注入（如 `ctx.approval_token`），且该字段不得来自请求体；对桥接工具强制注入 `additionalProperties: false` 或剥离保留字段。补负向测试：外部工具传 `approved=true` 必须 202/待审而非执行。

#### P0-2 审批消费与决策存在并发窗口，可能重复执行副作用

- 证据：`backend/app/modules/tools/approvals.py:150-170`，`has_approved_approval` 先查后改 `used_count`，无行锁；`:211-235` 的 `_ensure_decidable` 仅检查内存中的 `status`，未 `SELECT ... FOR UPDATE`。`approvals_router.py:126-150` 在批准后立即执行工具，整个“改状态 + 执行 + 记账”跨网络/线程。
- 影响：PostgreSQL 默认 Read Committed 下，两个并发批准/执行请求都可能读到 `pending`/未耗尽，导致同一工单被下发两次；SQLite 只是掩盖了问题。
- 修复：审批决策使用 `SELECT ... FOR UPDATE` 或条件更新 `UPDATE ... WHERE status='pending'` 并检查 rowcount；`used_count` 自增改为原子 SQL；把工具执行移到事务提交后的幂等执行器（带 `approval_id` 幂等键）。

#### P0-3 任意租户成员可上传、删除知识库文档（缺 `knowledge:write`）

- 证据：`backend/app/modules/knowledge/router.py:25-33` 上传、`:71-79` 删除均只依赖 `get_tenant_context`；同文件 `:82-92` 的 reparse 才在 service 层校验 `knowledge:write`。
- 实测：viewer 账号上传返回 201、删除他人在租户内的文档返回 200；跨租户访问返回 404（租户隔离本身是对的）。
- 影响：最低权限成员可以污染或清空团队知识库，直接破坏“可信知识资产”的产品承诺，也违反最小权限原则。
- 修复：为上传/删除/重解析统一加 `require_permission("knowledge:write")`；删除增加软删除与审计；补 6 角色 × 5 动作的权限矩阵测试。

#### P0-4 多空间账号登录进入死路，租户选择器永远不出现

- 证据：`backend/app/modules/auth/service.py:150-161` 对多空间且未传 `tenant_id` 的登录返回 400 `TENANT_REQUIRED`，空间列表放在 `error.details.tenants`；前端 `frontend/src/views/Login.vue:130-141` 捕获后再次调用**同样不带 `tenant_id`** 的 `authApi.login`，必然再次报错，异常被内层 `catch` 吞掉，`tenants` 始终为空。
- 影响：真实客户中“一人管多个小院/多基地”是常态，这类账号无法登录，属于主流程阻断。
- 修复：从错误 `details.tenants` 读取列表并渲染选择器；选择后带 `tenant_id` 重新登录。补 Playwright 用例：双空间账号登录 → 选择空间 → 进入工作台。

#### P0-5 前端 Tenant 契约与后端不一致，实测面包屑显示“未开通空间”

- 证据：后端返回 `{tenant_id, tenant_name, roles}`，前端类型却是 `{id?, name?, code?, status?}`（`frontend/src/types/api.ts:49-55`）；`stores/auth.ts:61` 用 `t.id` 匹配、`MainLayout.vue:73` 读 `auth.tenant?.name`。
- 实测：租户管理员登录后，页面左上角/面包屑显示“未开通空间”，而工作台数据正常；平台管理员 `/auth/me` 返回 `tenants: []`，所有业务路由被 `GlobalOverview` 覆盖（见 P1-7）。
- 影响：用户第一眼看到“未开通空间”，会怀疑账号或购买状态；同时导致空间切换、头像菜单等依赖 Tenant 字段的功能异常。
- 修复：统一契约（建议前端做一层 `TenantBrief` 适配器，兼容 `tenant_id/tenant_name` 与旧字段）；在 CI 加前后端类型生成或契约样例比对。

#### P0-6 自定义平台管理员用户名可被自助注册抢注（条件性提权）

- 证据：保留名单硬编码在 `backend/app/modules/tenants/signup.py:19-27`（admin/root/system/...），而运行时平台管理员名单来自配置 `PLATFORM_ADMIN_USERNAMES`（`backend/app/core/config.py:27,226`）；`auth/service.py:45-90` 只要用户名在配置名单中，登录时即追加 `platform_admin`。
- 触发条件：部署方把管理员名设为 `ops_admin` 等非默认值，且该管理员账号尚未创建；攻击者先自助注册该用户名 → 创建租户管理员 → 下次登录被 bootstrap 成平台管理员。
- 影响：平台级越权，可读全局统计、管理 MCP/供应商等。
- 修复：保留名单与配置名单取并集并统一小写比较；平台管理员账号只允许运维预置（seed/CLI），自助注册一律拒绝与配置名单同名；生产启动时校验“配置管理员已存在且不是自助注册来源”。

| P1-13 | 长耗时操作走同步请求，与 30s 前端超时冲突 | 班组运行同步（`agents/teams/router.py:230-279`）；专业助手/问答同步；实测问答在 mock 下尚可，接真实模型后 18-61s 很常见 | 用户看到“网络错误”但后端仍在跑。应默认 202 + task/run_id + SSE 订阅，前端提供“后台继续”入口 |

## 4. 五个角色视角

### 4.1 资深程序开发工程师：是否符合大厂要求？

**符合的部分**

- 分层与依赖方向正确，领域模块之间通过 service/registry 交互，没有“路由里写 SQL”的坏味道。
- Pydantic 2 + SQLAlchemy 2 + Alembic + 统一错误模型，类型与迁移纪律到位。
- 安全默认值总体偏保守：跨租户 404、密钥不回显、SSRF 白名单、审批参数哈希、审计留痕。
- 测试与 CI 不是装饰：655 测试、ruff、mypy、契约漂移检查都在流水线里。

**差距**

1. **授权校验分散**：有的在 router，有的在 service，有的漏掉（P0-3）。大厂做法是统一 `require_permission` 装饰器 + 权限矩阵测试，路由层不允许“裸 `get_tenant_context` 就写数据”。
2. **并发正确性未按生产数据库验证**：审批消费、任务状态迁移缺少行锁/条件更新；SQLite 下的绿灯会掩盖 PostgreSQL 下的竞态。
3. **注册表/目录存在双源**：`AGENT_DEFINITIONS` 与 `ToolRegistry` 各自维护，导致“列出但跑不了”。应单一事实源 + 启动自检。
4. **长任务同步化**：Agent/班组/工厂生成都有同步路径，接真实模型后会把 Web 层拖成“长连接队列”。应默认异步、同步仅保留小输入快路径。
5. **前端工程化欠债**：单包 1.4 MB、无 E2E、巨型组件、无 404、无刷新令牌。这些不是“以后再说”的优化，而是会直接变成线上故障的债。
6. **可观测性不足**：有审计和 `/metrics`，但缺端到端 trace（请求 → LLM → 工具 → 审批）、检索质量指标、队列积压告警。

**结论**：后端达到“优秀业务团队”水平，距离“大厂平台团队”主要差在**权限一致性、并发正确性、异步化与可观测性**这四项工程纪律，而不是架构能力。

### 4.2 资深产品经理：产品架构是否成立？

**成立的部分**

- 价值主张清晰：把“农业专家经验”变成“可检索、可引用、可纠错、可审核”的组织资产。
- 闭环设计有克制：反馈不直接进知识库，而是进候选队列由专家审核，避免模型幻觉污染。
- 能力分层合理：知识（事实）→ 助手（任务）→ 班组（协作）→ 设备（现场）→ 政策（合规）→ 市场/工厂（生态）。

**问题**

1. **主线过多，用户不知道“先用什么”。** 工作台、对话、问答、助手、班组、市场、工厂、知识库、设备、任务、政策、审核、成员、额度、设置、机器人、自生长，共 17 个入口。对站长/农技员，真正高频的只有 3 个：问一句、看任务、交资料。
2. **“自生长”是技术叙事，不是用户叙事。** 用户关心“它越用越懂我这片地”，而不是“候选知识/技能状态机/灰度发布”。应把“自生长”翻译成“经验沉淀进度、本月新增可信知识、专家纠错贡献榜”。
3. **平台管理员与租户管理员的边界在 UI 上不清楚。** 平台管理员进入业务页只看到总览（P1-7），但导航仍展示全部业务入口；用户会以为功能坏了。
4. **缺少“首次价值时刻”的设计。** 新租户开通后没有示例知识、没有引导任务、没有“10 分钟内得到第一个带引用答案”的路径。
5. **商业化分层未体现。** 额度、市场、工厂、私有化能力都在，但产品上没有“基础版/专业版/私有化”的能力边界与升级动机。

**建议的产品架构（收敛为四条主线）**

| 主线 | 用户问题 | 核心页面 | 成功指标 |
|---|---|---|---|
| 问与答 | 这块地现在怎么了 | 问答/对话（合并入口） | 首个带引用答案时长、采纳率 |
| 知识与经验 | 怎么把老专家的经验留下来 | 知识库 + 审核 + 贡献榜 | 可信知识条数、纠错采纳率 |
| 干活 | 今天要做什么、做到哪了 | 任务 + 班组 + 设备 | 任务完成率、超期率 |
| 治理与生态 | 怎么管人、管额度、接外部能力 | 成员/额度/设置/市场/工厂 | 活跃成员、集成数 |

### 4.3 重度用户（把它当生产力工具）：优势与缺陷

**会留下来的理由**

- 回答带引用，能点回原文，敢在给农户的方案里用。
- 纠错后由专家审核入库，团队知识真的会变厚。
- 设备告警、任务、IM 机器人在同一个平台，不用在四个群里找信息。
- 桌面端 + 本地文件 + 配对设备，现场也能用。

**每天会骂的点**

1. 30 分钟被踢出，正在写长回答时最难受（P1-4）。
2. 多基地账号登录不进去（P0-4）。
3. 提交反馈后不知道会不会入库、什么时候入库；候选列表缺少“我提交的”视角。
4. 知识库没有批量上传、目录/标签、失败重试批量操作；文档多了很难管。
5. 长任务没有可靠的进度与通知；切走页面就不知道跑完没有。
6. 没有“导出报告/周报”，专家审核结果无法直接用于汇报。
7. 机器人配置成功与否不透明（P1-11），不敢真的接到生产群。
8. 术语与英文状态多，给同事培训成本高。

**重度用户最想要的三件事**：稳定的会话（刷新令牌）、可信的任务进度（异步 + 通知）、可复用的产出（报告/模板/一键分享引用）。

### 4.4 小白用户（第一次接触）：难用在哪里？

按真实首次使用顺序：

1. **登录**：演示账号能进；但 README 里的账号与页面提示分散，多空间账号直接卡死（P0-4）。
2. **进入工作台**：三步引导是加分项；但示例问题点击后是否直接发起问答、是否消耗额度，没有说明。
3. **知识库**：空状态只有“选择文件/上传并解析”，没有“支持什么、解析要多久、失败怎么办”的就地说明；上传后状态字段是英文/技术码。
4. **提问**：高级选项折叠是好的；但“引用/置信度/候选问题”等概念没有解释，第一次看到会懵。
5. **反馈**：按钮语义不清（点赞/点踩/纠错），纠错表单要求用户自己组织“正确答案”，缺少结构化引导。
6. **设置**：默认 fake 模型却显示红色“异常”（P1-6），第一印象是系统坏了。
7. **导航**：17 项、4 组，图标+文字在展开态尚可，折叠态仅图标无提示（P2-6）。
8. **权限**：普通成员看不到管理入口是好事；但被 403 时的文案是否解释“找谁开通”未验证。

**新手三件套建议**：① 10 分钟引导任务（上传一份示例资料 → 问一个问题 → 看到引用 → 提交一次纠错）；② 全局术语表与就地 tooltip；③ 空状态全部改成“一个主按钮 + 一句为什么 + 一个示例”。

### 4.5 产品运营经理：怎么推广、怎么让人喜欢？

**定位建议**

- 不要卖“多智能体平台”，卖“**让每个小院都有一位不下班的农技专家，并且越用越懂本地**”。
- 首选 ICP：有稳定示范基地、有 1-2 位固定农技专家、已有微信/企微群的科技小院/农技推广站/农业企业基地。
- 切入场景：病虫害诊断问答 + 专家纠错沉淀 + 设备告警，这三件事最容易在 2 周内看到价值。

**增长路径**

1. **单点打透**：选 1 个作物、1 个基地、1 位专家，2 周陪跑，产出 30 条可信知识与 10 个真实案例。
2. **内容资产化**：把作物包/政策包/高频问答做成可安装的“行业包”，新客户一键获得可用知识，而不是从空库开始。
3. **IM 优先**：企业微信/钉钉/飞书机器人是最低门槛入口，先在群里回答，再引导到 Web 看引用与任务。
4. **专家网络**：把审核专家做成“认证专家”体系，贡献榜、署名、跨院复用分成，解决内容供给。
5. **样板复制**：一个县/一个产业带的标杆案例 → 相邻小院复制；用“同作物、同区域”的知识包降低冷启动。
6. **数据化运营**：激活 = 首次带引用回答；留存 = 每周 3 次提问或 1 次审核；扩购 = 成员数/设备数/额度消耗。

**运营必须补的产品能力**

- 邀请链接与批量开通（P1-12）、试用额度与到期提醒、Usage 报表、租户健康分、内容贡献榜、可分享的问答卡片/报告。

## 5. UI / UX 专项评审

### 5.1 亮点

- 深色玻璃体系贯穿登录、工作台、知识库、助手、审核，品牌识别度高。
- 设计令牌集中（`styles/design-system.css`），Element Plus 做了暗色桥接，整体不像“套模板”。
- 工作台信息架构合理：新手引导 → 待办 → 最近任务 → 知识库状态 → 待审核。
- 风险等级、任务状态、来源引用等信息密度控制得当，没有把后台做成 Excel。
- 真实截图控制台无 JS error，14 个页面均可渲染。

### 5.2 问题（按用户感知排序）

1. **面包屑“未开通空间”**（P0-5）：租户管理员实测仍显示，直接破坏信任。
2. **平台管理员所有页面都渲染总览**（P1-7）：URL/菜单/面包屑变了，内容没变，像“点了没反应”。
3. **设置页红色“异常”**（P1-6）：默认配置即报错，首次部署体验差。
4. **技术术语与英文状态**：`fake`、`active`、`worker.dispatch`、`LLM_PROVIDER`。
5. **空状态单薄**：同一张箱子插画用于知识库、审核、机器人，缺少行动指引。
6. **导航过载**：17 项、4 组；折叠后仅图标。
7. **移动端缺失**：固定侧栏与宽表格在手机上不可用。
8. **可访问性**：图标按钮无名称、对比度不足、状态颜色单编码。
9. **长任务反馈弱**：同步等待、无进度、无“后台继续”、无完成通知。
10. **缺少 404/错误边界**：错误 URL 与组件异常没有兜底页面。

### 5.3 评分

| 子项 | 分数 | 说明 |
|---|---:|---|
| 视觉一致性 | 8.0 | 令牌、圆角、阴影、渐变统一 |
| 信息架构 | 6.0 | 能力全但入口多，主线不突出 |
| 交互反馈 | 6.0 | 空/错/载有组件，但长任务与失败恢复弱 |
| 文案与术语 | 5.5 | 技术词裸露，业务语言不足 |
| 可访问性 | 3.0 | 键盘、对比度、aria 均欠缺 |
| 响应式/移动 | 3.0 | 基本未适配 |
| 综合 UI | 7.0 | 好看、统一，但细节契约有硬伤 |
| 综合 UX | 6.0 | 主流程能走通，关键分支会卡死 |

## 6. 开源对标：可以借鉴什么

> 许可证信息以各仓库当前 LICENSE 为准；下表只给选型方向，落地前需法务确认，尤其注意“Apache-2.0 + 附加条款”类项目。

### 6.1 第一梯队：直接对标的产品

| 项目 | 可借鉴点 | 不照搬的原因 / 许可提示 |
|---|---|---|
| **Dify** | 应用编排 DSL、知识库/工作流/观测一体的产品化、插件市场、模型供应商抽象 | 功能面过宽，直接对标会稀释农业纵深；许可证含附加条款（多租户 SaaS/品牌限制），商用需确认 |
| **Coze Studio / Coze Loop** | Bot/工作流/插件/评测的产品结构，低门槛创建体验 | 偏通用对话与 C 端，农业知识治理不足；以仓库 LICENSE 为准 |
| **FastGPT** | 知识库问答的开箱体验、引用展示、数据集管理 | 许可含附加限制；其检索与知识运营可借鉴，不建议整包引入 |
| **RAGFlow** | 文档解析（复杂 PDF/表格）、切片可视化、检索可解释 | Apache-2.0；解析链路重，适合借鉴“解析质量可视化”而非替换现有管线 |
| **Open WebUI** | 多模型/多用户/工具调用的前端交互、会话管理 | 偏通用聊天，不含农业业务；许可含品牌条款，注意 |
| **Langfuse** | LLM trace、prompt 版本、成本与质量分析 | 核心 MIT、企业功能商业授权；可自托管，是当前最值得补的可观测性组件 |
| **RAGAS / DeepEval** | 检索与生成评测指标（faithfulness、context recall 等） | Apache-2.0；直接用于评测门禁，补上“技能发布前评测”的可信度 |
| **Temporal** | 长事务/人工审批/重试的持久化工作流 | MIT；可解决审批与长任务的可靠性，但引入成本高，可先用“状态机 + 幂等表”过渡 |

### 6.2 第二梯队：架构与治理借鉴

| 方向 | 项目 | 借鉴点 |
|---|---|---|
| Agent 编排 | **LangGraph**（MIT） | 显式状态图、可中断/恢复、human-in-the-loop；比当前自定义 runner 更易做“审批中断后恢复” |
| 多 Agent 协议 | **MCP**（MIT）、**A2A**（Apache-2.0） | 工具与 Agent 互操作标准；当前已有 MCP 桥，建议补齐 A2A 的服务发现与任务生命周期 |
| 技能封装 | **Agent Skills** 开放格式 | 技能即目录（说明 + 脚本 + 资源），比纯 JSON definition 更利于专家贡献与复用 |
| 权限 | **Casbin**（Apache-2.0）/ **OPA**（Apache-2.0） | 把“角色-权限-资源-动作”从代码常量升级为策略；当前 `permissions.py` 适合先做矩阵测试，再考虑策略引擎 |
| 身份 | **Keycloak**（Apache-2.0） | 企业 SSO/OIDC/SAML、组织与成员邀请；当前自建 auth 可保留，企业版接 OIDC |
| 灰度 | **Unleash**（Apache-2.0） | 当前已有技能灰度，可借鉴其受众定向与实验指标 |
| 向量/检索 | **pgvector**（PostgreSQL License）、**Qdrant**（Apache-2.0）、**OpenSearch**（Apache-2.0） | 当前 pgvector + Python 回退；规模化后建议 pgvector HNSW + 全文检索混合，避免 500 块硬截断 |
| 文档解析 | **Docling**（MIT）、**Unstructured**（Apache-2.0） | 提升 PDF/表格/扫描件解析质量；**MinerU 为 AGPL-3.0，商用集成需谨慎** |
| 评测/红队 | **promptfoo**（MIT） | 提示词回归、红队用例，适合纳入 CI |
| 前端 | **VueUse**、**unplugin-vue-components** | 减少手写逻辑与包体；配合路由懒加载解决 1.4 MB 单包 |

### 6.3 建议的“借鉴顺序”

1. **先借工程能力，不借产品壳**：Langfuse（可观测）、RAGAS/DeepEval（评测）、promptfoo（提示回归）——直接提升现有闭环可信度。
2. **再借交互范式**：Dify/FastGPT 的“引用可点开、知识可解释、失败可重试”，改造知识库与问答页。
3. **最后借编排能力**：LangGraph/Temporal 解决“审批中断、长任务恢复”，A2A 解决跨平台 Agent 互操作。
4. **许可证红线**：AGPL（MinerU 等）不进入闭源分发链路；“Apache-2.0 + 附加条款”项目先法务评审再集成。

### 7.3 第 1 个季度：产品收敛与增长底座

1. **导航从 17 项收敛到 9 项**：工作台 / 问答 / 知识 / 任务 / 助手 / 班组 / 设备 / 治理 / 市场；对话与问答合并，政策并入知识或任务。

   - “专家 5 分钟处理一批纠错”（批量审核、差异对比、一键入库、贡献统计）。
3. **自生长的用户化表达**：把候选/技能/灰度翻译成“本月新增可信知识、专家纠错贡献、技能升级记录”；提供月度“知识健康报告”。

### 7.4 第 2-3 个季度：平台化与生态

## 10. 最终建议（按投入产出排序）

1. **先修 9 个 P0，两周内完成。** 这是“能不能给真实客户用”的门槛，尤其是知识库权限、审批旁路、多空间登录、Tenant 契约。
2. **把“问答 + 纠错沉淀”做成唯一主叙事。** 其他能力作为支撑，不要在首页平均用力。
3. **用真实模型与真实客户做一次 2 周陪跑。** 当前测试大量依赖 fake provider，真实延迟、失败率、成本会暴露下一批问题。
4. **补可观测性与评测，再谈自生长。** 没有 trace 与 recall 指标，“越用越聪明”无法证明。
5. **产品收敛优先于功能扩张。** 17 个入口减到 9 个，比再加 5 个 Agent 更能提升留存。

> 这套系统的底子足以支撑“农业垂直领域最好的知识型 Agent 平台”这个目标。当前最值得做的不是继续加能力，而是把已有的能力变成**可信、稳定、第一次就能用明白**的产品。

## 12. 对话工作台升级（2026-10-26，v1.8.0）

§11 收口的是「能跑 → 敢用」；本轮按产品需求把对话页从「问答框」升级为
「可交付任务的工作台」，落地第一期（附件阅读）与第二期（对话内生成能力 +
过程步骤可见）。

### 12.1 范围与决策

| 需求 | 决策 | 落地位置 |
|---|---|---|
| 照片 / 文档让模型读取 | 检索为主（附件内容进上下文，不参与路由打分） | `app/modules/chat/attachments.py` |
| 对话内生成能力 | 管理员执行 / 成员申请（权限口径与能力中心完全一致，不开旁路） | `app/modules/chat/capability.py` |
| 过程步骤实时可见 | 分期实施，先做一期 + 二期 | `app/core/progress.py`、`app/modules/chat/stream.py` |

### 12.2 关键实现约束（后续改动须遵守）

1. **阶段名是前后端稳定契约**：`progress.py` 的阶段只追加、不改含义
   （reading / routing / retrieving / thinking / tool_call / generating）。
2. **意图识别宁可漏判不可误判**：创建类必须同时命中创建动词与能力名词，
   含疑问词一律降级为提问（"怎么做个助手"是咨询，不是指令）。
3. **流式响应不得持有请求级 ORM session**：FastAPI 在响应体流式输出前就关闭
   依赖 session，继续访问 ORM 属性会抛 `DetachedInstanceError`（生产环境挂死、
   测试却通过——测试夹具的 session 析构顺序与生产不一致）。流自持 session，
   序列化后再提交。
4. **断流不重试**：POST 重试会重复提交，改为以服务端记录为准降级，如实呈现
   未完成状态。
5. **安全默认值**：对话内生成的能力工具白名单固定 `knowledge.search`（只读）、
   知识范围固定 `tenant`，对应 `risk=low`；副作用工具必须在能力中心显式添加。

### 12.3 本轮修复的缺陷

- **生产环境 SSE 挂死**（见 12.2 第 3 条）：流式响应持有请求级 session，
  在 uvicorn 下 `ChatSession.id` 抛 `DetachedInstanceError`，对话无响应；
  已补回归用例（模拟真实依赖析构顺序）。
- **能力卡片永远不渲染**：对话内生成能力的消息 `routed_by="local"`，而前端
  路由来源映射未登记该取值，读取徽章样式时抛错中断整条消息渲染。
